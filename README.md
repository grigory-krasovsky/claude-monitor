# Claude Usage Monitor

Телеграм-бот, который следит за пятичасовым и недельным лимитами Claude Code
и держит в чате самообновляющееся статусное сообщение. Один бот обслуживает
несколько аккаунтов Claude: каждый пользователь подключает свой в личке с ботом,
регистрация закрытая — заявки одобряет администратор.

Данные берутся из недокументированного эндпоинта Anthropic
`GET https://api.anthropic.com/api/oauth/usage` (см.
[issue #202](https://github.com/Maciek-roboblog/Claude-Code-Usage-Monitor/issues/202)).
Это серверные цифры, поэтому монитору не нужен доступ к локальным jsonl-логам
Claude Code и учитывается работа со всех устройств — именно поэтому его можно
держать на VPS.

## Что умеет

- закрытая регистрация: первый `/register` делает администратором, остальные
  становятся заявками, которые админ одобряет кнопками под сообщением;
- опрос лимитов каждого подключённого аккаунта раз в 3 минуты (TTL эндпоинта —
  180 с, чаще ходить нельзя);
- одно самообновляющееся статусное сообщение в чате каждого пользователя;
- алерт, если API недоступен два опроса подряд; при восстановлении он снимается сам;
- аккаунты, токены и id сообщений хранятся в PostgreSQL, токены — зашифрованными
  (AES-256-GCM, см. [Хранение токенов](#хранение-токенов)).

## Команды

Все команды — в личке с ботом. В группах бот отвечает только на `/chatid` и `/help`.

| Команда | Кому | Что делает |
|---|---|---|
| `/register` | всем | подать заявку; первый зарегистрировавшийся становится администратором |
| `/token <refresh token>` | одобренным | подключить аккаунт Claude (см. ниже); сообщение с токеном бот сразу удаляет |
| `/status` | одобренным | пересоздать своё статусное сообщение последним в чате |
| `/forget` | одобренным | стереть токены и сообщения; обычный пользователь удаляется целиком, у админа сохраняется роль |
| `/users` | админу | список аккаунтов: имя, статус, подключён ли токен (сами токены не показываются) |
| `/revoke <chat id>` | админу | отозвать доступ: статус REJECTED, токены стёрты, статус из чата удалён |
| `/chatid`, `/help`, `/start` | всем | id чата и справка |

Пока заявка не одобрена, остальные команды получают короткий отказ без каких-либо
данных.

### Как проходит регистрация

1. Пользователь пишет боту `/register`. Если администратора ещё нет, им становится
   он сам. Гонку двух одновременных «первых» решает уникальный индекс в базе:
   администратор всегда ровно один.
2. Иначе администратору приходит «Заявка от Имя (@username, id)» с кнопками
   «Одобрить» / «Отклонить». Повторный `/register` админа не беспокоит: на заявку
   на рассмотрении бот отвечает «уже на рассмотрении», на отклонённую — «отклонена».
   Исключение — заявка, которую не удалось доставить админу: повторный `/register`
   отправит её заново.
3. После решения кнопки с сообщения снимаются, к нему дописывается «✅ одобрено» или
   «❌ отклонено», а заявитель получает уведомление — при одобрении с инструкцией
   про `/token`. Нажимать кнопки может только администратор.

## Где взять токен Anthropic

Нужен **refresh token из отдельного логина** `claude`:

```bash
CLAUDE_CONFIG_DIR=~/.claude-monitor claude login
```

Затем из `~/.claude-monitor/.credentials.json` берётся значение
`claudeAiOauth.refreshToken` (`sk-ant-ort01-...`) и отправляется боту:
`/token sk-ant-ort01-...`. Бот удаляет сообщение, обменивает токен, делает пробный
запрос лимитов и при успехе сразу запускает мониторинг.

Отдельный каталог обязателен: Anthropic ротирует refresh token при каждом обмене,
и бот, получив копию токена основного `~/.claude`, разлогинил бы локальный
Claude Code. Access token живёт 8 часов, дальше бот обновляет его сам и сохраняет
ротированный refresh token в базе.

**`claude setup-token` не подходит.** Его токен имеет только scope
`user:inference`, и `/api/oauth/usage` отвечает ему
`403 OAuth token does not meet scope requirement user:profile`.

Если `/token` не прошёл, бот объясняет причину: недействительный токен (400/401),
нет scope `user:profile` (403 `permission_error`), гео-блокировка
(403 `Request not allowed`, см. ниже).

## Хранение токенов

Access и refresh token каждого аккаунта лежат в колонках `account.access_token` и
`refresh_token` только в зашифрованном виде: AES-256-GCM с ключом из
`TOKEN_ENCRYPTION_KEY`, случайный IV на каждую запись, формат
`v1:` + base64(IV ‖ шифротекст ‖ тег). В качестве AAD используется chat_id
аккаунта, поэтому шифротекст нельзя переставить в чужую строку — он просто не
расшифруется. Шифрует и расшифровывает только `AccountRepository`; ни токены, ни
ключ в логи не пишутся.

От чего это защищает: от утечки дампа или бэкапа базы и от доступа к volume
`pg-data` — без ключа токены из них бесполезны. От чего **не** защищает: от доступа
к самому серверу. Ключ лежит в `.env` рядом с `docker-compose.yml` на том же VPS и
в окружении контейнера, так что тот, кто получил shell на хосте (или права на
docker), получает и ключ, и базу. Поэтому бэкапы базы стоит хранить отдельно от
`.env`, а сам ключ — только в секретах GitHub.

Ключ генерируется один раз:

```bash
openssl rand -base64 32
```

```powershell
[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))
```

Без ключа, с ключом не в base64 или не из 32 байт приложение не стартует и пишет,
что не так (сам ключ в сообщение не попадает). **Потеря или смена ключа означает,
что все сохранённые токены перестают читаться**: бот не падает, но мониторинг таких
аккаунтов останавливается, их статусы убираются из чата, а пользователи получают
просьбу заново прислать `/token`. То же происходит с отдельной строкой, если её
значение подменили или оно записано в открытом виде.

## Как ведут себя сообщения

В чате каждого пользователя бот держит максимум два своих сообщения: статус и, при
необходимости, алерт. Статус переписывается на месте раз в 15 секунд и всегда
остаётся последним.

- **API недоступен** — после двух неудачных опросов подряд поднимается алерт,
  при восстановлении он снимается сам;
- **статус удалили руками** — бот создаёт новый, но только если Telegram прямо
  ответил, что сообщения нет. На `429 Too Many Requests` бот молчит `retry_after`
  секунд, если пользователь заблокировал бота — час, а не плодит дубли.

Опрос и отрисовка разведены намеренно: данные тянутся раз в 3 минуты, а сообщение
перерисовывается раз в 15 секунд, поэтому обратный отсчёт и шкала времени идут
непрерывно. Возраст данных подписан в сообщении, чтобы проценты токенов не
выглядели секундными.

Id сообщений лежат в базе — после редеплоя бот продолжает править то же самое
сообщение, а не бросает его и заводит новое.

Каждое окно показывается двумя соревнующимися шкалами: расход токенов (зелёная →
жёлтая → красная по мере роста) против доли прошедшего времени окна (синяя). Если
токены обгоняют время, лимит кончится раньше, чем окно сбросится:

```
🟢 Пятичасовое окно — сброс в 17:40 (через 1 ч 44 мин)
🟩🟩🟩🟩🟩🟩⬜⬜⬜⬜ токены 61%
🟦🟦🟦🟦⬜⬜⬜⬜⬜⬜ время 42%
⚡ расход опережает время на 19 п.п.
```

## Быстрый старт

```bash
cp .env.example .env
# заполнить TELEGRAM_BOT_TOKEN, POSTGRES_PASSWORD и TOKEN_ENCRYPTION_KEY (openssl rand -base64 32)
docker compose up -d --build
docker compose logs -f
```

Затем написать боту `/register` (первый станет администратором) и `/token ...`.

## Переход с однопользовательской версии

Раньше бот обслуживал один чат из `TELEGRAM_CHAT_ID` с токенами из `ANTHROPIC_*`
и файлов `/data/tokens.json`, `/data/board.json`. При первом старте новой версии
этот chat id один раз импортируется в базу как одобренный пользователь (USER) с
этими токенами — файлы свежее окружения, — и бот продолжает править то же
статусное сообщение. Volume `monitor-data:/data` для этого сохранён.

Роль администратора импорт не даёт: её даёт только первый `/register`, как и
всем остальным, — первый зарегистрировавшийся становится администратором. Если
это сделает владелец, его запись повысится до ADMIN с сохранением токенов; если
админ уже есть, владелец остаётся обычным подключённым пользователем. Импорт отмечается в базе и не повторяется, поэтому после него
`TELEGRAM_CHAT_ID` и `ANTHROPIC_*` можно убрать — приложение стартует и без них,
а `/forget` не будет «воскрешён» следующим рестартом.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | — | токен от @BotFather |
| `POSTGRES_PASSWORD` | — | пароль пользователя `monitor` в PostgreSQL; обязателен для docker compose |
| `TOKEN_ENCRYPTION_KEY` | — | ключ шифрования токенов в базе: base64 от 32 байт; обязателен, см. [Хранение токенов](#хранение-токенов) |
| `SPRING_DATASOURCE_URL` | `jdbc:postgresql://localhost:5432/monitor` | адрес базы; в docker compose задан на сервис `db` |
| `SPRING_DATASOURCE_USERNAME` / `_PASSWORD` | `monitor` / `monitor` | учётка базы; в compose берутся из `POSTGRES_PASSWORD` |
| `POLL_INTERVAL` | `3m` | интервал опроса, меньше 3m ставить нельзя |
| `RENDER_INTERVAL` | `15s` | как часто перерисовывается статусное сообщение |
| `THRESHOLDS` | `50,75,90,95` | пороги утилизации в процентах |
| `TIMEZONE` | `Europe/Moscow` | часовой пояс для времени сброса |
| `HTTPS_PROXY` | — | HTTP-прокси для исходящих запросов, если нужен |
| `TELEGRAM_CHAT_ID` | — | только для импорта прежнего владельца |
| `ANTHROPIC_REFRESH_TOKEN` / `ANTHROPIC_ACCESS_TOKEN` | — | только для импорта прежнего владельца |

### Про 403 от Anthropic

`api.anthropic.com` отдаёт `403 Request not allowed` для запросов из заблокированных
регионов. Если VPS стоит в таком регионе, задайте `HTTPS_PROXY` — Java, в отличие от
curl, эту переменную сама не читает, поэтому приложение прокидывает её в HTTP-клиент
явно.

## Деплой на VPS

Готовить сервер вручную не нужно — на нём достаточно Docker с плагином
`docker compose` (v2, без дефиса) и пользователя, имеющего к нему доступ.
Пайплайн на push в `master` делает всё остальное: сборка и тесты → образ в GHCR →
ssh на сервер, где создаётся каталог, копируется `docker-compose.yml`,
генерируется `.env` и выполняется `docker compose pull && up -d`.

Compose поднимает два сервиса: `db` (`postgres:17-alpine`, данные на volume
`pg-data`, порт наружу не публикуется) и `monitor`, который стартует после
healthcheck базы. Схему создаёт Flyway при запуске приложения.

`.env` на сервере целиком пересобирается из секретов при каждом деплое, так что
единственный источник правды — GitHub. Править его на сервере бесполезно,
изменения затрутся следующим push.

Обязательные секреты репозитория:

| Секрет | Назначение |
|---|---|
| `VPS_HOST` | адрес сервера |
| `VPS_USER` | пользователь ssh |
| `VPS_PASSWORD` | пароль ssh |
| `TELEGRAM_BOT_TOKEN` | токен от @BotFather |
| `POSTGRES_PASSWORD` | пароль базы; без него деплой останавливается |
| `TOKEN_ENCRYPTION_KEY` | ключ шифрования токенов (`openssl rand -base64 32`); без него деплой останавливается |

`POSTGRES_PASSWORD` читается Postgres только при первой инициализации volume:
если сменить секрет позже, пароль придётся поменять и внутри базы
(`ALTER USER monitor PASSWORD '...'`), иначе монитор не подключится.

`TOKEN_ENCRYPTION_KEY` задаётся один раз и больше не меняется: со сменой секрета
все сохранённые токены перестанут читаться, и пользователям придётся заново
прислать `/token`. Сохраните копию ключа вне GitHub — прочитать значение секрета
обратно GitHub не даёт.

Деплой идёт в `~/claude-usage-monitor` — домашний каталог доступен на запись любому
пользователю, в отличие от `/opt`. Абсолютный путь можно задать через `VPS_PATH`,
если у пользователя есть туда права.

Необязательные — задаются, только если нужно отойти от значений по умолчанию:
`VPS_PORT` (22), `VPS_PATH` (`claude-usage-monitor`), `POLL_INTERVAL` (`3m`),
`RENDER_INTERVAL` (`15s`), `THRESHOLDS` (`50,75,90,95`), `TIMEZONE` (`Europe/Moscow`),
`HTTPS_PROXY` (пусто). `TELEGRAM_CHAT_ID`, `ANTHROPIC_ACCESS_TOKEN` и
`ANTHROPIC_REFRESH_TOKEN` нужны только для импорта прежнего владельца и после
него могут быть удалены.

## Локальная разработка

Тесты поднимают PostgreSQL через Testcontainers, так что нужен запущенный Docker:

```bash
./mvnw test
```

Для `spring-boot:run` нужна база на `localhost:5432` (база, пользователь и пароль —
`monitor`), например:

```bash
docker run -d --name monitor-db -p 5432:5432 \
  -e POSTGRES_DB=monitor -e POSTGRES_USER=monitor -e POSTGRES_PASSWORD=monitor postgres:17-alpine
TOKEN_ENCRYPTION_KEY=$(openssl rand -base64 32) ./mvnw spring-boot:run
```

Ключ из примера живёт до перезапуска: чтобы токены в локальной базе пережили
рестарт, сохраните его и передавайте тот же. Тестам ключ не нужен — у них свой
фиксированный (`TestBeans.TOKEN_KEY`).
